# Fincas overview (table and cards)

`/b/estates` keeps `DashboardBComponent` and the existing creation modal. Both views render the same `EstateOverview.items`; switching views only persists `domora-estates-view` (`table` / `cards`). Invalid preferences fall back to table. Page size is 12 in either view.

## API contracts

Existing `GET /api/v1/estates` remains an array with its existing scope and metrics. New read endpoints are declared before `:estateId` and restricted to roles A/B, like accounting summaries. Role B additionally requires both JWT `estateIds` and its `administratorId`; deleted estates are excluded. No frontend parameter widens this scope.

- `GET /api/v1/estates/overview`: `page` (default 1), `pageSize` (default 12, max 60), `search` (max 100), `filter` (`all`, `issues`, `pending`, `requests`), comma-separated backend `types`, `sort` (`name`, `ownersCount`, `balance`, `activeIssues`, `pendingAmount`), `direction` (`asc`, `desc`). Defaults: name ascending. Search covers name/address/streetNumber/location and normalizes accents. All scoped aggregates are computed in a fixed number of bulk queries; filtering and sorting run on the server before pagination. A stable ID tie-breaker prevents pagination ambiguity. The server clamps pages beyond the last page.
- Response: explicit `items`, `page`, `pageSize`, `total`, `totalPages`, `pendingLabel`, plus unfiltered scoped `summary` with communities/properties/pendingRequests. Financial amounts are decimal strings in the API and converted by the Angular service, matching existing monetary DTO handling. Table formatting uses `Intl.NumberFormat('es-ES', {currency: 'EUR', ...})`, two decimals.
- `GET /api/v1/estates/overview/export.xlsx`: same search/filter/types/sort/direction validation and authorization as overview, without page/pageSize. Reuses the exact scoped aggregation and selection before pagination. Exports all matching rows (maximum 10,000; larger selections return 400 without truncation) in a real XLSX workbook using the existing backend ExcelJS dependency. Columns: community name, formatted address, owners, open incidences, treasury balance, ordinary pending fees. Counts and EUR amounts are numeric cells; names/addresses stay literal strings. The sheet freezes and filters its header row.
- `GET /api/v1/estates/management-search?q=...`: minimum two trimmed characters, max 100. At most five results per domain (community, owner, issue), 15 total. Database matching is case-insensitive, using real fields: estate name/address/streetNumber/location; owner User.fullName or ExternalOwner.fullName; Issue.title/description/ref. Tax IDs and issue descriptions are never returned. Queries are individually bounded; issue results cannot be displaced by owner results. Owners must be linked/non-revoked and users/properties/estates non-deleted. External owners promoted to users are excluded. This endpoint is separate from the existing linking `/estates/search`.

All three frontend searches are independent: scope selector filters its accessible `/estates` list; header search calls management-search; local search calls overview. The latter two debounce 275 ms and ignore stale responses. Local search/type/sort resets page 1. View switching preserves page and results. The UI sends `filter=all`: the four quick-filter chips and current-scope badge have been removed. A themed multi-select dropdown combines estate types (OR), remains open while checking options, supports arrows/Escape/outside dismissal and clearing. Type, Excel download and view controls share the local-search row on desktop; toolbar sorting/direction controls have been removed while sortable table headers remain. The download uses current search/types/sort across all pages, reports failures and prevents duplicate clicks; the header search starts at the viewport midpoint where space permits.

## Owners and finances

`ownersCount` counts linked, non-revoked `Propietario` users on non-deleted properties, excluding deleted users. User IDs are unique per estate. Add unpromoted ExternalOwner records on those properties. Where a country and non-empty fiscal ID exist, the country plus uppercase ID with whitespace/dots/hyphens removed is the internal identity; otherwise retain user ID/external-owner ID. Never deduplicate by name. Fiscal IDs are used only internally and are not in overview/search responses.

Treasury is the existing 57x debit-minus-credit balance across years, excluding closing/year_opening. `LedgerQueryService.treasuryBalancesForEstates()` now supplies both accounting/summary and overview, so the definition cannot drift. There are no per-estate summary requests.

The schema has an explicit `ReceiptKind.cuota_ordinaria`, distinct from derrama, fondo_reserva, saldo_anterior, interest and other charges. Therefore the UI says **Cuotas pendientes**, and sums only ordinary receipts' outstanding amounts in Pendiente/Parcial/Devuelto. This deliberately differs from accounting `delinquency`, which includes other kinds. No due-date restriction is added. The quick pending filter uses this same ordinary-fee aggregate.

Incidences reuse ACTIVE_ISSUE_STATUSES unchanged. Pending requests are AdhesionRequest.pending, never onboarding requests or tickets. No community state is fabricated.

## Official Catastro facade cache

`CatastroFacadeService` normalizes RC (trim, whitespace removal, uppercase; valid alphanumeric 14/18/20 characters), takes the first 14 characters and calls the fixed official HTTPS WFS endpoint with `StoredQuerie_id=GetBuildingByParcel`. Uses the existing fast-xml-parser, validates XML, rejects DOCTYPE/entities, caps body at 2 MiB and times out after 10 seconds. WFS redirects are rejected.

Only Building/document/Document/documentLink is read. Only the observed `ovc.catastro.meh.es` facade service path is accepted, without credentials/non-default ports, with a matching parcel parameter. Catastro currently emits an HTTP documentLink; its identical HTTPS photo endpoint was verified and is used to avoid mixed content. No image proxy or client-supplied URL fetch is introduced. The frontend CSP permits only this additional image host.

Live verification on 2026-10-14: both StoredQuerie_id and StoredQuery_id returned Building GML for the published reference 1907401VK4810H; production code uses the documented StoredQuerie_id. The returned facade URL over HTTPS responded 200 image/jpeg without a redirect. The required sample 7874101WF4777S0001UI normalizes to parcel 7874101WF4777S; its live WFS response contained no building/photo, which is supported.

During the final isolated API validation, Catastro subsequently returned its HTML maintenance page announcing 15:15–19:00. Creation and RC updates remained successful, the attempt timestamp was saved with a null URL, and the real backfill recorded the negative attempt. A fresh positive end-to-end cache run must wait for WFS availability; positive parsing/cache behavior is covered by deterministic tests, and the official WFS/photo endpoints had been verified before maintenance.

Migration `20261014120000_estate_catastro_facade` adds nullable catastroFacadeUrl/catastroFacadeResolvedAt. URL is a cache, RC stays authoritative. Create with RC, update supplying RC, and existing Catastro import resolve after the principal DB transaction. Updates supplying RC invalidate atomically, even if an earlier snapshot had the same reference. Compare-and-set prevents late responses writing over a different RC. WFS and cache-write failures do not undo/report failure for a completed principal mutation. ResolvedAt records the last attempt, including a negative result. The overview never contacts WFS.

Explicit backfill, after migration and backend build:

`node backend/scripts/backfill-catastro-facades.cjs --limit=200`

Runs sequentially with a 250 ms pause, bounded batches, non-deleted estates with RC and no cached URL. Default selects never-attempted estates; `--retry` includes prior negative attempts. Each estate is processed once per run via ID keyset cursor. Failures are logged without aborting the remaining batch. A missing photo or failed img displays a neutral building icon, never a replacement photograph.

Rollback: stop using the new views/columns, then drop the two nullable cache columns if required. The overview is additive; no existing array API needs migration.

## UI and validation

Header: EstateScopeSelectorComponent + EstateManagementSearchComponent. Dashboard owns query state. EstateOverviewViewsComponent is presentation only; EstateFacadeThumbnailComponent serves small table and wide card photos. Skeletons are in EstateOverviewSkeletonComponent. Cards show photo/name/address, an upper-right incidences badge, and compact owners/balance/ordinary-fee pending metrics. Both views use the same `pendingAmount` and currency formatting. The desktop grid has four columns; narrower layouts use two or one. Table adds Ver finca and orders its centered metric columns as owners, incidences, pending fees, balance. No status, setup column or speculative actions. Existing setup service/detail flows remain.

Native controls, accessible links, dialog focus/keyboard handling, semantic table/aria-sort, view aria-pressed, tokens and both themes are retained. Table remains a horizontally scrollable table on mobile; cards do not become the automatic mobile view. Detail issue deep links fetch an issue outside the first page and verify its property belongs to the loaded estate before presenting it.
